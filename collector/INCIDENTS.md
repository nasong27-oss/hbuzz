## 2026-09-16 — 아침 자동 발송 실패 (메일이 아예 안 나감)

### 증상
- 08:00 발송 잡이 돌았으나 **메일이 발송되지 않음**. 수신자 12명 중 아무도 못 받음.
- 사용자 문의 시각 08:41. 확인해 보니 `reports/2026-09-16.html` 파일 자체가 없었음.

### 확인된 사실 (로그 기반)
`data/launchd.log` 타임라인:

```
07:30:04  [생성] 시작
          (※ "네트워크 준비됨" 로그 라인 없음 → 네트워크 대기 40회(120초) 전부 실패)
          (※ [수집] 라인도 한 줄도 안 찍힘)
08:00:05  [발송] 시작
08:00:xx  [발송] 오늘자 리포트 없음 → 발송 건너뜀 (생성 잡 미완/실패?)
08:11:08  [발송] 종료 (exit=0)
08:43:07  [생성] 종료 (exit=0)   ← 생성이 73분 만에 끝남. 리포트는 이때 생성됨
```

- 생성 잡은 **죽지 않았고**, 비정상적으로 느리게(73분) 완료됨.
- 08:43 이후 수동 확인 시 네트워크는 정상(SMTP/구글뉴스 모두 OK), 뉴스 수집기 단독 실행도
  정상(11건, 66초)이었음 → **코드 자체의 영구적 결함은 아님**.
- 08:56 수동 발송으로 12명 전원에게 정상 리포트 발송 완료(뉴스 링크 포함).

### 추정 원인 (가설 — 재검증 여지 있음)
1. **기상 직후 네트워크 미연결**이 1차 원인으로 추정.
   - 근거: `run_generate.sh`의 네트워크 대기 루프(40회 × 3초 = 120초)가 전부 실패해
     "네트워크 준비됨" 로그를 남기지 못함. 즉 **07:32까지도 네트워크가 안 붙음**.
2. 네트워크가 없는 상태로 수집이 시작 → 각 수집기가 타임아웃/재시도
   (`collect_all`의 0건 재시도 3회 + 백오프 3초/8초, 수집기 15~30초 타임아웃)를 반복.
   - 사이트 15개 × 재시도 × 타임아웃이 누적되며 **생성 73분** 소요로 추정.
3. 08:00 발송 시점에 리포트가 없자, 당시 `run_send.sh`는 **그냥 "건너뜀"으로 종료** →
   그날 메일이 영영 안 나감(재시도 경로가 전혀 없었음).

### 조치 (커밋 73eb24d)
- `run_generate.sh`: 네트워크 대기 **120초 → 10분**(100회 × 6초). 끝내 실패 시 로그에 명시.
- `run_send.sh`: **자가치유** 도입.
  - SMTP 대기 5분으로 연장.
  - 오늘자 리포트가 없으면 스킵하지 않고, 생성 잡이 아직 돌면 **최대 40분 대기**(30초 폴링).
  - 생성 프로세스도 없고 리포트도 없으면 **발송 잡이 직접 `main.py --dry-run` 실행 후 발송**.
- `pgrep` 패턴 버그 수정: macOS venv 파이썬은 `ps`에 **대문자 `Python`**으로 떠서
  `pgrep -f "python main.py"`가 생성 잡을 감지하지 못했음 → `-i`(대소문자 무시) 적용.
  (이 버그가 남아 있었다면 자가치유가 "생성 중인데도 없다고 판단"해 **중복 생성**할 뻔했음)

### 남은 의문 / 재분석 포인트
- **왜 네트워크가 120초 넘게 안 붙었는가?** 다크웨이크(dark wake) 상태에서 Wi-Fi가 늦게
  붙은 것으로 보이나 확증 없음. `pmset -g log` 로 07:30 전후 wake/네트워크 이벤트 확인 필요.
- **73분이 정말 네트워크 부재 때문인가?** 수집기별 소요 시간 로그가 없어 단정 불가.
  → 수집기별 경과시간을 로그에 남기면 다음 발생 시 즉시 판별 가능(미구현).
- 네트워크 없이 시작했을 때 **조기 실패(fail-fast) 후 재시작**이 더 나은지,
  지금처럼 오래 걸려도 완주하는 게 나은지 정책 결정 필요.
- 자가치유가 실제로 동작하는지는 **아직 실전 검증 전**(다음 장애 때 확인).
